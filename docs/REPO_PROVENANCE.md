# 仓库历史说明（Provenance）

这份文档回答一个问题：**这个仓库的"连续开发历史"里，哪些是真的，哪些是本地留档，
以及别人怎么自己验证。**

写它的原因很直接——「过程可信」的前提是经得起核查。如果一份历史需要靠 README 自述
才能成立，那它就不可信。所以这里把构成摊开，并给出可执行的验证命令。

---

## 一、历史是怎么形成的

| 时间段 | 提交数 | 性质 | 说明 |
| --- | --- | --- | --- |
| 2026-10-01 → 10-21 | 19 | **按开发顺序补录** | 时间戳为重建，因此都落在整点（09:00、10:00、14:00…）。代码演进顺序与踩坑记录是真实的，但**不能当作"每天在写代码"的证据** |
| 2026-10-22 → 10-23 | 56 | **真实连续开发** | 含秒级时间戳，提交间隔从几十秒到几小时不等，反映真实的迭代节奏 |

合计 75 个提交、15 个 `feature/*` 或 `fix/*` 分支、16 个 `--no-ff` 合并提交、6 个版本标签。

### 为什么补录的部分也要写清楚

如果只看 `git log`，2026-10-01 到 10-21 的提交看起来完全正常：一天一两个 commit，
消息规范，有分支有合并。**看不出是补录的**——直到有人注意到时间全是整点。

与其等人发现，不如自己说清楚。这也是本项目在数据口径上的一贯做法：
不知道的标"估算"，没有的标"不存在"，补录的就标"补录"。

## 二、三处「看起来像，但其实还不存在」的东西

这三条是最容易被误读的，单独列出来。

### 1. `Merge PR #19` 不是 GitHub 上的 PR

合并提交的消息里写了 `Merge PR #19: …`，但仓库推上 GitHub 之前没有远端，那边**没有编号为 #19 的 PR**。
它是本地 `git merge --no-ff` 时手写的留档，作用是让人在 `git log` 里能看出"这次合并对应哪个功能包"。

**怎么补**：PR 无法事后补建（GitHub 要求源分支未合并）。想要真实 PR 轨迹，
只能在后续开发中真的开分支 → push → 开 PR → 合并。仓库推上去之后，
建议把下一个功能按这个流程走一遍，让 `gh pr list` 里有第一条真实记录。

推送仓库的方法见 [README「上传到 GitHub」](../README.md#上传到-github怎么拿到-repo-地址)。

### 2. `closes #26` 不会关闭任何东西

同理，`docs/ISSUES.md` 里的 #1–#30 是**本地编号表**，不是 GitHub Issue。

**怎么补**：`tools/publish_to_github.sh` 会按 #1→#30 的顺序把它们真实建出来。
因为 Issue 编号是仓库级序列（与 PR 共享），脚本会先检查仓库里是否已有 Issue/PR，
有就中止，避免编号错位。

```bash
git remote add origin git@github.com:OWNER/REPO.git
git push -u origin main --tags

bash tools/publish_to_github.sh          # 预演：只打印要建什么
bash tools/publish_to_github.sh --apply  # 真的建
```

建完之后，`closes #26` 才真正指向一个对象。

### 3. CI 徽章目前是静态的

`.github/workflows/ci.yml` 是真实可用的配置（3.8/3.11/3.13 跑全量 + 3.7 零依赖 job），
但它**从未在 GitHub 上运行过**——因为仓库还没 push。

所以 README 顶部放的是 shields 静态徽章，不是 Actions 状态徽章。
push 之后把 README 里注释掉的那行取消注释、替换 `OWNER/REPO`，才是真实的构建状态。

## 三、怎么自己验证

```bash
python tools/check_history.py
```

这个脚本把"连续开发"拆成 6 条可证伪的约束，任一条不满足就以退出码 1 结束：

| 约束 | 违反意味着什么 |
| --- | --- |
| 父子提交时间严格递增 | 发布提交早于它要发布的内容——典型的事后改历史痕迹 |
| `author date == committer date` | 两者不一致，通常说明只改了其中一个时间 |
| 提交时间不在未来 | 为了让项目"看起来开发了很久"而把时间往前挪 |
| 每个 `feature/*` / `fix/*` 分支都有合并提交 | 快进合并会抹掉分支存在过的痕迹 |
| 标签指向存在且可达的提交 | 空标签 / 悬空标签 |
| 提交信息带规范前缀 | 变更无法分类、无法追溯 |

当前状态：

```
提交数：75
[ok] 父子提交时间严格递增
[ok] author 与 committer 时间一致
[ok] 提交时间不在未来
[ok] 每个 feature/fix 分支都有合并提交
[ok] 标签指向存在且可达的提交
[ok] 提交信息带规范前缀
----------------------------------------------
合并提交（--no-ff）：16 个
结果：通过
```

校验器本身也有测试（`tests/test_history.py`，10 项）：在临时仓库里**刻意造出**时间倒挂、
author/committer 不一致、未来时间戳、快进合并、非法前缀等违规历史，确认每一条都能被抓出来。
一个永远只会说"通过"的校验器等于没有。

### 还能查什么

```bash
# 分支与合并轨迹
git log --graph --oneline --all --date-order

# 某个版本区间做了什么
git log --oneline v1.4.0..v1.5.0

# 单个提交改了哪些文件
git show --stat <commit>

# 确认没有把密钥提交进历史
git log --all -p -S "sk-" --oneline | head
```

## 四、如果要拿去交课程 / 竞赛

建议这样表述，既准确又不吃亏：

> 项目采用 Git 连续开发：75 个提交、15 个功能分支、16 次 `--no-ff` 合并、6 个版本标签，
> 每个功能走「开分支 → 分主题提交 → 合并」流程。
> 其中 2026-10-01 至 10-21 的 19 个提交为按开发顺序补录（时间戳重建），
> 10-22 起为真实连续开发记录。仓库提供 `tools/check_history.py` 供核查历史自洽性。

**不要**说"开发了 23 天"或"有 30 个 Issue"——前者不准确，后者在 push 之前不成立。
评审者一旦核查，这两句话会让整份材料失信；而主动说明反而说明你知道自己在做什么。

## 五、这份文档本身怎么维护

- 历史构成变化（比如又补录了一段）→ 更新第一节的表格
- 补建了真实 Issue / PR / CI → 把第二节对应条目改成"已建"，并附链接
- `check_history.py` 新增约束 → 同步第三节的表格

如果哪天这份文档和仓库实际状态不一致，**以 `git log` 为准**，并把它改对。
